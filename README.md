# 🩸 Blood Cancer Detection System

> ⚠️ **Academic Project Disclaimer**
> This is a final year college project built for educational and research purposes only.
> Predictions generated by this system are **NOT** a certified medical diagnosis and must
> never replace professional medical judgment. All findings should be confirmed by a
> qualified hematologist/oncologist.

A hospital-style web system where doctors register and get approved by an admin, then use
a trained PyTorch model to screen blood cell images across 11 cell classes, track patient
history, and submit feedback. Admins review/approve/reject doctor registrations, manage
doctor accounts, and monitor system-wide stats.

---

## Features

- **Doctor workflow:** register → wait for admin approval (with login ID + password issued
  by email/SMS) → log in → run predictions → view patient history → submit feedback
- **Admin workflow:** review pending registrations → approve/reject → manage existing
  doctors (edit name/email/mobile/gender/login ID/password, or delete) → view feedback →
  forgot-password recovery via security question → change password
- **AI prediction:** ResNet50-based model classifies blood cell images into 11 types
  (BAS, EBO, EOS, LYT, MON, MYB, MYO, NGB, NGS, OTHER, PMO), returning a confidence score,
  symptoms, and general medical guidance for each class
- **Live stat boxes** on the landing page and admin dashboard: registered doctors,
  predictions made, patients screened, positive/negative case counts, feedback received
- **JWT-based authentication** with separate roles for doctors and admins
- **Clean direct URLs** — starting the server and opening it in a browser lands you on the
  public homepage directly; the admin panel is reachable only by typing `/admin` (it is
  never linked from any public page)

## Tech stack

- **Backend:** FastAPI (Python), SQLAlchemy ORM, JWT auth (`python-jose`), bcrypt password hashing
- **Database:** SQLite, split across **4 separate files** by concern (see below) instead
  of one shared database — easier to inspect and back up independently
- **Frontend:** Plain HTML/CSS/JS (no build step, no framework) — served directly by
  FastAPI, so backend and frontend run as a single process on one port
- **ML:** PyTorch — ResNet50 backbone with a custom classification head

## 1. Setup

```bash
git clone <your-repo-url>
cd blood_cancer_system
pip install -r requirements.txt
python init_db.py
```

`init_db.py` creates all four database files and seeds one default admin account:

| Field | Value |
|---|---|
| Email | `admin@hospital.com` |
| Password | `Admin@123` |
| Security question | "What is your favorite color?" |
| Security answer | `blue` |

**Change these immediately** after your first login, via the admin dashboard's
"Change Password" option.

## 2. Run it

```bash
uvicorn app.main:app --reload
```

Open **http://localhost:8000/** — that's the public landing page, served directly.

- Doctor login: `http://localhost:8000/doctor/login`
- Doctor registration: `http://localhost:8000/register`
- **Admin login (not linked anywhere — type it directly):** `http://localhost:8000/admin`

Backend and frontend run together as one FastAPI app — there's no separate frontend
server, and no need to double-click any `.html` file.

## 3. Plug in your trained model

Your trained model file goes here (**not included in this repo** — see note below):

```
app/ml_model/best_model.pth
```

> 📦 **This file is gitignored.** At ~90MB it's close to GitHub's 100MB per-file limit,
> and model weights are best kept out of git history anyway since they change
> independently of the code. After cloning this repo, copy your own
> `best_model.pth` into `app/ml_model/` before running the server — otherwise
> `/predict` will return an error saying the model isn't loaded (everything else
> in the app still works fine without it).
> For sharing the actual weights, use a release asset, Git LFS, or cloud storage link.

The architecture is already wired up in `app/ml_model/load_model.py` to match a
**ResNet50 backbone with a custom classification head** (Dropout → Linear(2048→256) →
ReLU → Dropout → Linear(256→11)), trained on 11 classes:

```
BAS, EBO, EOS, LYT, MON, MYB, MYO, NGB, NGS, OTHER, PMO
```

If your model uses a different architecture or class list, update
`app/ml_model/load_model.py` accordingly. Symptoms/medicines text per class live in
`app/utils/ml_predict.py`, alongside `POSITIVE_CLASSES` — the set of classes treated as
an abnormal/positive finding for the dashboard's positive/negative stat boxes.

> ⚠️ The symptoms/medicines text in `ml_predict.py` is placeholder guidance for an
> academic project, not verified clinical content — replace with reviewed material if
> this is ever used beyond a coursework demo.

## 4. Email & SMS notifications

Currently **simulated** — approval/rejection messages are printed to the console and
logged to `sent_emails.log` / `sent_sms.log` instead of actually being sent.

To go live:
- **Email:** edit `app/utils/email_service.py`, set `SIMULATE = False`, add SMTP credentials
- **SMS:** edit `app/utils/sms_service.py`, set `SIMULATE = False`, integrate a provider (Twilio, MSG91, etc.)

## 5. Database structure

Data is split across **four separate SQLite files**, all kept together inside a
`database/` folder (instead of loose files scattered at the project root), so each
concern is easy to find and inspect independently:

| File | Tables | Why grouped together |
|---|---|---|
| `database/admins.db` | `admins` | Standalone — admin accounts only |
| `database/doctors.db` | `doctors`, `registration_requests` | A `Doctor` row is created directly from an approved `RegistrationRequest` in one transaction, with a real foreign key between them |
| `database/patients.db` | `patients`, `predictions` | Every `Prediction` belongs to a `Patient` via a real foreign key, queried together on every history lookup |
| `database/feedback.db` | `feedback` | Standalone — doctor feedback submissions |

> SQLite can't enforce foreign keys *across* separate files. `Patient.doctor_id` and
> `Feedback.doctor_id` still store the doctor's ID for reference, but as plain integer
> columns rather than enforced foreign keys, since `doctors.db` is a different file.

## 7. End-to-end flow (tested)

1. Doctor submits registration → `POST /register`
2. Admin views pending requests → `GET /admin/requests`
3. Admin approves (issues login ID + password) → `POST /admin/requests/{id}/approve`
   → sends email + SMS, **or** rejects with a reason → `POST /admin/requests/{id}/reject`
4. Doctor logs in with the issued credentials → `POST /doctor/login`
5. Doctor uploads a cell image + patient name → `POST /predict` → auto-generates a
   Patient ID, runs the model, saves the record
6. Doctor searches patient history by Patient ID → `GET /patients/{id}`
7. Doctor submits feedback → `POST /feedback`
8. Admin views feedback list → `GET /admin/feedback`
9. Admin edits or deletes a doctor's details → `PUT` / `DELETE /admin/doctors/{id}`
10. Admin resets a forgotten password via security question → `POST /admin/forgot-password/question`
    then `POST /admin/forgot-password/reset`
11. Admin changes their password while logged in → `POST /admin/change-password`
12. Anyone can view live counts → `GET /stats`
